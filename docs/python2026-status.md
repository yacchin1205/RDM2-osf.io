# Python 2026 Status

## 方針

この作業の目的は、単にテストを通すことではない。

目的は、Python 本体や関連ライブラリの更新によって露出した不整合を取り除き、現行の実行環境で成立する状態へ寄せることにある。

したがって、

- 目の前の failure を黙らせるだけの回避策を優先しない
- upstream(CenterForOpenscience/osf.io) に存在しない独自パッチを安易に入れない
- 依存関係、ライブラリ間の前提差、API 変更点を先に確認する
- 症状ではなく根本原因に遡って修正する

ことを徹底する。

## 実務上の指針

- collecting で止まる場合は、まず import error や依存バージョン差を確認する
- runtime failure でも、まずライブラリの version set と upstream の実装差を確認する
- `bytes` / `str`、削除済み API、deprecated API のような failure は、局所パッチより先に依存不整合を疑う
- テストコードの修正も、テストを無理に通すためではなく、古い前提を現行 Python / ライブラリに合わせるために行う

## Upstream パッチの扱い

upstream(CenterForOpenscience/osf.io)は我々の数年前からのフォーク元であり、差分が非常に大きくなってしまったが、彼らのパッチには参考になる部分が多い。しかしながら、 それらのパッチは、そのまま安全に取り込めるとは限らない。

特に upstream の変更には、

- 機能追加
- 既存挙動の変更
- 運用前提の変更
- この fork には存在しない仕様や整理

が含まれることがある。

この作業はバージョンアッププロジェクトであり、機能改修プロジェクトではない。したがって、

- upstream を参照する目的は、互換修正や依存更新の方向を知るためである
- upstream にあるからという理由だけで機能変更を持ち込まない
- この fork の現行機能と挙動は原則維持する
- upstream 変更を取り込むときは、それが互換修正なのか、仕様変更なのかを必ず区別する

ことを意識する。

## 禁止事項

- 「目の前の failure を早く前に進める」ことを判断基準にしない
- 根因未確認のまま、その場しのぎのクソパッチを入れない
- 事実確認前に、原因や方針を断定しない
- 「最短で通す」を独立した価値として扱わない
- すべての修正は、upstream 整合性・保守性・説明可能性・誤修正リスクとのトレードオフで判断する
- 局所的な近道で一時的に前進しても、後で説明・修正・再判断が必要になるなら、総時間ではむしろ遅いとみなす
